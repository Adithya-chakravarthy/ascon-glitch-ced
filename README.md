# Concurrent error detection for Ascon under clock glitches

RTL, scripts and raw measurement data for the letter

> ADITHYA C, "Concurrent Error Detection for Ascon Under Clock Glitches:
> FPGA Measurements and a Pipelined Parity Checker," submitted to *IEEE Embedded Systems
> Letters*, 2026.

A round-based Ascon-AEAD128 core runs on a Digilent Cmod A7-35T (Artix-7, XC7A35T-1).
An MMCM-based clock generator shortens one chosen initialization round to 2.89-3.69 ns,
a carry-chain TDC measures every shortened cycle, and the full 320-bit state is read
back after the glitched round. Since we know exactly which state bits flipped, we can
tell for every fault whether a checker's code covers it and compare that with the alarm
the checker actually raised on the board.

## Layout

```
rtl/           core, checkers, UART interface, glitch clock, TDC (Verilog)
constraints/   pin and timing constraints
sim/           testbenches and test vectors
vivado/        project creation, builds and programming (Tcl)
scripts/       campaign tool, checker generator, analysis (Python)
data/
  glitch/      raw campaign logs, one JSON line per encryption
  sta/         per-bit setup slack of every build
  groups/      parity groups of the group-parity builds
  cost.csv     LUT/FF counts and WNS reported by Vivado
  sim_coverage.csv   coverage for stuck-at faults at the S-box outputs
```

## Checkers

| VARIANT | checker |
|---|---|
| 0 | none |
| 1 | S-box parity, 1 bit per S-box |
| 5 | S-box interleaved parity, 2 bits per S-box |
| 6 | S-box CRC-3, 3 bits per S-box |
| 7 | S-box CRC-3 with the signatures registered and compared one cycle later |
| 2 | global parity of the state |
| 3 | k-group parity, generated by `scripts/gen_gpar.py` (`--chunk 6`: pipelined prediction) |
| 4 | duplication |

The S-box signatures follow Kaur et al., IEEE TCAS-II 69(4), 2022.

Build labels in the data are `v<VARIANT>_<name>`. For example `v3_i32c` has 32 interleaved
groups with pipelined prediction, `v3_sta24` checks the 24 slowest bits exactly, and the
suffixes `_s2` and `_s3` mark the same design implemented with another strategy
(`_s2` came out identical to the default placement).

## Requirements

- Vivado (we used 2025.2) and a Cmod A7-35T for the hardware part
- Python 3.9 or newer; `pip install -r requirements.txt` (pyserial) for talking to the board.
  The analysis scripts only use the standard library.

## Reproducing the numbers from the raw data

No hardware needed:

```
cd scripts
python paper_tables.py            # Table I and the points in Fig. 2
python analyze_campaigns.py       # per-build report, written to results/summary.md
python sta_compare.py ../data/sta/v0_state.csv "../data/glitch/*_v0_*.jsonl"
python sim_coverage.py            # simulated coverage, results/sim_coverage.csv
```

## Building the bitstreams

In the Vivado Tcl console:

```
cd <path to this repository>/vivado
source create_project.tcl
source build_all.tcl
```

`build_all.tcl` runs every configuration of the paper (roughly 3 minutes each) and puts
bitstreams, timing reports and the cost table into `build/`. A single configuration:

```
source build.tcl
build v3_i32c 3 interleave 32 6
```

`build_select.tcl` repeats the timing-based bit selection described in the paper.
If Vivado cannot start Python, `set PY C:/path/to/python.exe` before sourcing.

## Running a campaign

Program a bitstream from the Vivado Tcl console:

```
set BIT v3_i32c
source program.tcl
```

then, on the PC:

```
cd scripts
python glitch_campaign.py selftest
python glitch_campaign.py clean --config v3_i32c
python glitch_campaign.py campaign --config v3_i32c
```

The campaign applies 4000 glitches at ten lengths (3.69 to 2.89 ns) in initialization
rounds 1-11, always with seed 7, so every build sees the same glitch sequence. Logs are
written to `results/glitch/`. Use `--port COMx` if the board is not found automatically.

## Log format

The first line of each `.jsonl` file holds the settings (`variant`, `phases`, `rounds`,
`seed`, `config`, ...). Every further line is one encryption with an empty message:

| field | meaning |
|---|---|
| `t` | glitched initialization round |
| `phase` | fine-phase step; the glitched cycle lasts `phase * 1/(56 * 600 MHz)` = `phase * 29.76 ps` |
| `key`, `nonce` | random inputs |
| `flips` | state bits that differ from the expected state after round `t`, index `64*w + b` |
| `tag_ok`, `timeout`, `ctrl` | tag correct, core timed out, cycle count differed |
| `alarm` | checker alarm |
| `tdc` | TDC taps reached in the glitched cycle |

Files starting with `clean_` contain 2000 encryptions without a glitch per build.

## Simulation

The testbenches in `sim/` run in the Vivado simulator. `tb_ascon_aead128` reads
`vectors.txt`; if the simulator does not find it, set `FALLBACK_PATH` in the testbench to
the full path of `sim/vectors.txt`.
